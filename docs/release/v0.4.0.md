# cli-bot v0.4.0

**A command now needs your approval unless cli-bot recognises every part of
it as read-only.**

Before this release, a command ran the moment it was chosen, unless the
model flagged it or its text happened to contain one of nineteen configured
substrings. A code review measured that gate against fourteen plainly
destructive commands: twelve of them ran with no prompt at all, including
`rm -fr ~/projects`, `shred -u ~/.ssh/id_ed25519`, and
`curl -fsSL <url> | sh`.

## What changed

cli-bot now parses the command it is about to run and sorts it into one of
three tiers:

| Tier | Examples | What happens |
|---|---|---|
| Read-only | `ls -la`, `git log --oneline`, `ls \| wc -l` | Runs straight away, as before |
| State-changing | `npm install`, `touch notes.md`, `echo x > f` | Shown and confirmed; `Enter` means yes |
| Destructive | `rm -fr x`, `git clean -fdx`, `sudo systemctl stop sshd` | Shown with a stronger prompt; `Enter` means no |

Classification works on the parsed command, so flag order, flag spelling,
extra spaces, quoting, pipes, redirections, `$(...)`, and a `sudo` prefix
cannot change the answer. A command cli-bot cannot parse, or whose program
it does not recognise, is confirmed rather than run.

## If you run cli-bot from a script

This is the change most likely to affect you. A command that needs approval
now fails when there is no terminal to ask, instead of running.

- `--yes` (or `-y`) pre-approves the state-changing tier.
- `--i-approve-destructive-commands` pre-approves the destructive tier as
  well, and implies `--yes`. It has no short form and, deliberately, no
  configuration key.
- `[safety] assume_yes = true` makes `--yes` the default for every run.

```bash
cli-bot --yes "create a build directory"
```

## Configuration

`[safety]` gains three keys and `[ui]` gains one. Every one has a default,
so a `cli-bot.toml` written for an earlier version keeps working, and
`require_confirmation` and `destructive_substrings` keep their old meaning.

- `read_only_commands` — the commands that run without asking
- `destructive_commands` — extra commands for the strong tier
- `assume_yes` — the default for `--yes`
- `[ui] confirmation_prompt` — the wording for the state-changing tier

The full list, and the built-in rules for programs whose risk depends on
their flags, are in
[docs/configuration.md](https://github.com/joelee/cli-bot/blob/v0.4.0/docs/configuration.md).

## Also in this release

- The default model is now `ornith-1.5:9b`, chosen from
  [the v0.3.2 model benchmark](https://github.com/joelee/cli-bot/blob/v0.4.0/docs/models-benchmark-report-v0.3.2.md).
- Releases are tag-driven through the `Release` workflow, which checks the
  tag and the release records, builds binaries, publishes to crates.io after
  the `release` environment is approved, and creates the GitHub release.
- A declined command is now recorded in session memory, so a follow-up
  question has the context.
- The confirmation, selection, and request prompts sit behind a `Prompter`
  trait, so the approve, decline, and select paths are covered by tests for
  the first time. Line coverage is 90.62%.

## Upgrading

```bash
cargo install cli-bot --force
```

Nothing in your configuration or session files needs changing. If a command
you run often now asks for confirmation and you would rather it did not, add
it to `read_only_commands`:

```toml
[safety]
read_only_commands = ["ls", "cat", "git status", "git log", "kubectl get"]
```
